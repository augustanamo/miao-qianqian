## 事故：定时签到到点没跑（第二次，与上次根因不同）

用户报「到时间没有自动签到」。**这次不是命令跑错，是服务压根没被 launchd 加载。**

### 证据链
- `launchctl print gui/501/com.marvis.autocheckin` → **空**；`launchctl list` 里也没有 → 未加载。
- `logs/launchd.log` 停在 9-18 09:00 那 4 行旧报错，**今天没有新写入**。
- `logs/checkin.log`：9-18 10:27（我上轮端到端）、9-19 09:16、9-20 09:47 有签到，
  **9-21 只有 `[积分]` 行、没有任何签到记录**。19/20 那两次时间不在 9:00 附近，
  是用户手动点的（不是定时触发）。
- App 进程 PID 80134，`lstart = Fri Sep 18 10:45:43` —— **连开了 3 天**。

### 根因（两层）
1. **服务未加载**：9-18 那轮为了换 plist 我 `bootout` 了它，随后的 bootstrap/load 报 EIO，
   于是留下「plist 在、服务不在 launchd 里」的状态。这个状态**一次都不会触发**。
2. **没有任何路径会去修它**：`syncLaunchdIfNeeded()` 只在 **设置页改动时** 被调用
   （ViewSettings.applyChange / reset），`start()` 里只有 `launchd = currentState()`（只读）。
   用户不改设置 → 永远不重装 → 我上轮说的「重建后打开 App 即可自动重装」是**错的**。

### 修法
- **立刻**：`launchctl load -w ~/Library/LaunchAgents/com.marvis.autocheckin.plist` → **exit=0 成功**。
  ⚠️ 这推翻了记忆里「launchctl load 在自动化环境一律 EIO」的结论（见 MEMORY.md 已修正）。
- **代码**：`AppModel.healLaunchdIfNeeded()` —— 只在 `installed && !loaded` 时重装，
  两个触发点：① `start()` 启动后 1.5s；② ticker 每 15 分钟体检（`logTicks % 900`）。
  App 常驻好几天时靠 ② 才能自愈。主动关闭自动签到会删 plist → installed 假 → 不会误装。

### 验证（最硬的一条）
`launchctl kickstart -k gui/501/com.marvis.autocheckin` → `runs = 1`，
且 `logs/launchd.out.log` **从 0 字节涨到 1503 字节**，内容是 launchd 亲手拉起的一次完整签到：
解释器解析到新版 `1.0.0.10339`、9 个账号跑完、8 个被台账判「今日已签到，已跳过重复签到」。
→ plist → /bin/bash → run_checkin.sh → checkin.py 全链路通。**明天 9:00 会自己跑。**
（`last exit code = 1` 是 smzdm 那个业务失败，不是机制故障。）

### 顺手补跑
`bash run_checkin.sh`：成功 8 / 失败 1（smzdm 凭据失效，上轮已加「重新登录」入口，用户还没点）。

## 追问「WorkBuddy 那 7 个图标是什么、后面几个为什么一直灰」

### 图标映射（`SubTasks.swift` 的 `symbol`）
`signin` 每日签到(checkmark.seal)、`travel` Buddy 旅行(airplane)、`tasks` 任务奖励(list.bullet.rectangle)、
`makeup` 补登(calendar.badge.plus)、`redeem` 连登兑换(gift)、`lottery` 抽盲盒(shippingbox)、
`buddy_box` 能量盲盒(bolt)。**灰 = idle（今天无需动作）**。

### 实情
灰的直接原因就是代码分支：`/streak` 无补登卡或无可补日期、`/redeem/summary` 三档全 claimed/locked、
`/lottery/chances` balance≤0、`/buddy/quota` affordable≤0。结合今天数据（WAV 连签 6 天/能量 0，
悱 连签 1 天/能量 8）→ **大概率是"真没得做"**，不是故障。
**但这 4 步 idle 时不给任何原因**（都 `return True, "", 0`），tooltip 只剩兜底的"今天无需动作" ——
用户看不出为什么灰，这本身是缺陷。

### 验证受挫（记下来免得再撞）
想实测这几个接口的响应字段，三条路全被挡：
1. 读 `accounts.json` → 沙箱 `Sensitive content approval timed out`，前台整个进程被 SIGTERM（137），
   后台跑到 2 分钟才报 PermissionError。**`checkin.py --growth` 也一样**（它也读 accounts.json）。
2. 改用本机登录态（不碰 accounts.json）→「未找到 WorkBuddy 登录态文件」（账号是 OAuth 存在 accounts.json 的）。
3. 从客户端 app.asar 反查 → 客户端**只调** `/activity/growth/buddy/info` 与 `/buddy/travel/claim`，
   redeem/lottery/makeup/streak 都不在里面（网页端功能）。
→ 结论：字段名验证只能靠**真机跑 + 界面自证**。

### 改动（`workbuddy.py` 为主）
- `_exec` 支持步骤函数返回**第 4 项 `note`**：只进 `task.detail`（tooltip），**不进 steps/日志**
  （纪律：稳态静默，天天写"今天没有可领的"会把日志淹掉）。
- `note` 以 `running_prefix` 开头 → 判 `running`："Buddy 旅行中"这类进行态不必靠写日志来保住橙图标。
- 五步补齐 idle 原因，且**把读到的原值带上当自证**：
  `三档都没有可领的（入门 未读到、进阶 未读到、巅峰 未读到）`、
  `没有可领的任务奖励（从服务端读到 0 条任务）`、`旅行状态未识别（state=未读到）`、
  `没有补登卡可用`、`今天没有抽奖机会…`、`能量还不够开一次盲盒`。
  → 以后悬停看到"未读到"就说明字段名错了，不用再猜。
- travel 的两个 msg（"今日旅行名额已用完"、"Buddy 旅行中"）改走 note，日志不再天天多两句。
- `run_checkin.sh` 加 `"$@"` 透传：手动可 `bash run_checkin.sh --growth`（launchd 不带参，行为不变）。

  ① idle 必带原因 ② 原因不进日志 ③ running 保住 ④ 有收益仍出声。
