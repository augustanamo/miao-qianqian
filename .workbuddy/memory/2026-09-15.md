### 挖出的真 bug：Trae JWT 过期后不续期

日志证据链：`00:00 签到成功` → `09:22 起全部 FAIL（HTTP 200 + 错误码 1001）` →
`[积分] 查询失败：HTTP 401`。因为 `TraeClient` 写的是 `token = self.token or self.get_token()`，
而调用方**总会**把 `accounts.json` 里的旧 JWT 传进来，所以 `self.token` 永不为空 →
**永远不换新 token**。JWT 只有约 8 小时有效（长效的是 session，约 14 天）。

修法：`trae_api.py` 加 `_post_authed()`，`credits`/`status`/`checkin` 统一走它，
命中鉴权失败（**HTTP 401/403 或业务码 1001**，只看 HTTP 状态码会漏判）就用 session 换新 JWT 重试一次。

**实网验证（只读）**：修后 `checkin.py --credits --json --only 132trae` 返回 `剩余 2657.31 积分`（此前一直是 401）。
Trae 状态接口真实响应也拿到了：
`{"checked_in": true, "code": 0, "credits": 150, "did_checked_in": true, ...}`
→ **今天确实早就签过了，旧代码却又发了一次 claim 并报成"签到成功"**，正是用户说的现象。

### 签到去重

- 原生预检：Trae/WorkBuddy/联想有只读状态接口；**Bilibili / 京东没有**，靠台账兜底。
- 台账 `logs/checkin_state.json`：只存 `{日期:{账号:{platform,ok,credits,message,at}}}`，
  保留 14 天，**不含任何凭证**（已用脚本断言过）。命中则跳过、记为已签到、不发请求。
- 安全方向：预检判不出来就照常签到，**宁可多发一次请求也不漏签**。
- Trae 预检命中时不再调 claim —— 用 `AssertionError` 假客户端断言过。

### 根因一：SwiftUI `Menu` 标签忽略内容里的 `.frame()`

**不是图标资源问题，是 SwiftUI 的坑。** `Menu` 的标签会按 `NSImage` 的**自然点尺寸**绘制内容，
内容里的 `.frame(width:14,height:14)` 被吃掉。`workbuddy.png` 是 512×512 @72dpi →
自然尺寸就是 **512pt**，面板被撑到 ~550pt。

离屏实测（`NSHostingView` + `fittingSize`）—— 脚本已固化：`.workbuddy/tools/probe_layout.swift`
（`xcrun swift .workbuddy/tools/probe_layout.swift` 直接跑）：

| 容器 | fittingSize |
|---|---|
| `Menu` 标签内置图标（原写法） | **548 × 512** ← workbuddy.png(512pt) 撑出来的宽度，与截图反推的「面板 ~550pt」完全吻合 |
| `Button` + `.buttonStyle(.plain)` | **88 × 32** ✅ 与设计稿一致 |
| `Menu` + 图标放标签外 | 73 × 16 ✅ 也可行但图标跑到框外 |

**修法**：新增账号面板的平台下拉由 `Menu` 换成 **`Button` + `.popover`**（`platformMenu`），
图标留在胶囊内且守规矩。另外 `PlatformIcon.image()` 加了 34pt 渲染上限（`clampPointSize`）兜底。

**布局复算**（窗口 1280 / 侧栏 240 / 页面留白 38×2 → 可用 964）：
- 修复前：面板内容 ~550pt → 列表只剩 **391pt**，而列表五列需要 ≥506pt → 裁切。与用户截图完全对上。
- 修复后：面板 358pt → 列表 **583pt** ✓。

### 根因二：京东登录态接口已失效

`passport.jd.com/user/petName/getUserInfoForMini609.action` **现在返回 186,375 字节的京东首页 HTML**
（不是 JSON），判定逻辑要求响应以 `{` 开头 → 永远走不到 ok → `browser_login.py` 一直轮询到 600s 超时，
浏览器自然也不关。

**换成** `api.m.jd.com/client.action?functionId=signBeanIndex&appid=ld`（只读京豆签到首页数据）：
未登录返回 `{"code":"3","errorMessage":"用户未登录"}`，登录有效 `code=="0"`。
顺带能读出**京豆余额**（`totalBeanNum`/`beanNum` 容错取值），京东那行积分不再恒为「—」。

注意两个陷阱：
- `signBeanAct`（签到本身）对无效 cookie 返回 `402「活动现在挤不进去呀」`，**不是**登录信号，别拿它判登录态。
- 同一请求实测一次 `200/code3`、一次 `403` —— 这个接口本身不稳，所以等待策略不能只靠状态分类。

### 根因三：联想签到页 `$CONFIG` 改了写法

线上页面早已从「一个对象字面量」改成**先 `$CONFIG = {}` 再逐行赋值**：

```js
$CONFIG = {};
$CONFIG.token = "lv91...";
$CONFIG.lenovoId = "0";
$CONFIG.loginName = "";
$CONFIG.signState = ""        ← 最后一项没有分号
```

旧正则 `\$CONFIG\s*=\s*(\{.*?\})\s*;` 只命中第一行的 `{}` → 解析结果恒空 → **校验永远失败**。

- 新解析器：逐条匹配 `$CONFIG.key = 值`，值只允许「带引号字符串」或「不含空白/;/<> 的裸值」。
  **值模式必须收紧**：否则最后一项缺分号时会一路吞掉后面的 `<script>` 和 CSS 文本（踩过）。
- 附带发现：**未登录页面同样有 `$CONFIG` 和 token**，所以新增 `_is_logged_in()` 判定
  （`lenovoId` 非 "0"、`loginName` 非空、或 `signState` 非空）。
  这条同时修好了联想**签到本身** —— 以前所有联想账号都会报「无法解析签到页」。

### 对策：登录态校验改成三态，等待不再可能无限

`browser_login.py` 的 `verify()` 契约从 `(ok, nickname, uid, msg)` 改成 **`(state, nickname, uid, msg)`**：

| state | 含义 | 处理 |
|---|---|---|
| `ok` | 平台明确说已登录 | 立即保存、关窗 |
| `pending` | 平台明确说还没登录 | 继续等 |
| `unknown` | 接口改版/风控/网络异常，判不了 | 连续 3 次 → 按「关键 Cookie 已捕获」保存 |

双保险：`UNKNOWN_ACCEPT_STREAK=3` + `CAPTURE_GRACE_SECONDS=120`（关键 Cookie 到手后最多再等 120s）。
安全性依据：`pt_key`/`pt_pin`、`SESSDATA` 只在登录成功后由平台下发，齐了本身就是强登录信号。
**注意「有值」才算捕获**：游客态可能出现 `pt_key=` 这种空值，只比键名会让宽限期提前开跑
（`_cookie_map()` 判空值）。
另外补了 20s 一次的进度日志、`with` 退出兜底关窗、以及账号名兜底用 `pt_pin`（手机号只留尾 4 位）。

### 验证

- Python：`py_compile` 全过；联想解析器 6 个用例（线上真实页面 / 已登录模拟 / 旧字面量 / 缺分号 / 空页面）；
  京东 `probe_login` 三个分支（invalid / ok+余额 / 接口变更→unknown）；三态等待策略用状态序列模拟过。
- Swift：`swiftc -parse` + `-typecheck`（arm64-apple-macos13.0 + MacOSX plugin-path）→ **0 error**，
  Theme/ViewAccounts 0 warning。离屏 `fittingSize` 探针实测了三种容器的真实尺寸。
- 预览：`.workbuddy/preview/登录与尺寸修复说明.html`（含 before/after 布局按真实 pt 数画的示意图），
  已用无头 Chrome 渲染核对。

## 第七轮：哔哩哔哩 / 京东签到失败 —— 两个都是平台接口问题，引出了「平台受限」第三态

用户反馈「哔哩哔哩和京东签到失败了」。实测下来两个平台的失败原因完全不同，
但都不是 cookie 的问题；顺手把「平台侧不可用」从「失败」里拆了出来。

### 根因一：B站签到端点根本不存在（HTTP 404）

`bilibili.py` 一直在打 `GET /x/web-interface/checkin` —— 这个路径**不存在**，
返回的是 HTML 错误页 → `_parse_json` 失败 → `response 解析失败（HTTP 404）`。
`data.bonus.doubloons` 那套解析是照着不存在的响应写的。

**正确入口**：`GET /x/member/web/exp/reward`（成长中心 → 每日任务 → 登录 的
「领取」按钮背后的接口）。B站**早已取消独立签到入口**，每日登录经验由
"有效登录行为"发放，这个接口是唯一可编程触达的领取/查询入口，天然幂等。
返回 `{"code":0,"data":{"login":bool,"watch":bool,"coins":num,"share":bool,...}}`。

- 收益单位是**经验**不是硬币（硬币余额仍走 nav 的 `money`）。每日登录 +5 经验。
- `already` 语义要按**调用前**的 `login` 判定：调用前就是 true → 本次没重复领取；
  调用前 false → 是这次领取触发的，稍后再查一次确认到账。
- 未登录的错误码有**两个**：无 cookie / 空 SESSDATA → `code -101 账号未登录`；
  **非法的 SESSDATA → `code -400 请求错误`**（HTTP 200）。所以 -400 要再用
  只读 `nav()` 复核一次才能定性，不能直接当 cookie 失效。

### 根因二：京东京豆签到活动已下线（服务端）

- `https://bean.m.jd.com/` 与 `/bean/signIndex.action` 都 **302 到京东错误页**
  （`jfe-lb.jd.com/.../jfe.html?err=52`），京豆签到网页版没了。
- `signBeanAct` 对未签名请求统一返回 `402「活动现在挤不进去呀，待会再来试试吧」`；
  GET 形式返回 `code="0" + errorCode="S109「当前签到人数较多，请稍晚再来」`。
- **换 appid / client / body 全部无效**：`appid=ld` → 402；无 appid →
  `600 signature verification failed`；`appid=jd-bean` → `1 no access`；
  `dailySignIn`/`signBeanIndex` 之外的 functionId → `2 the current API does not exist`。
- `signBeanIndex`（我们用来校验登录态的只读接口）现在返回
  `{"code":"0","errorCode":"DG-9999","errorMessage":"系统异常"}` —— code 仍是 "0"
  所以登录态校验还能用，但**拿不到京豆余额**了。

**⚠️ 新踩的坑**：`code=="0"` **不等于成功**。旧代码 `if code == "0"` 就当成
「今日已签到（幂等）」，而 S109 软失败正是 code="0"+errorCode!="0" —— 会被
误报成"已签到"！现在必须先看 `errorCode` 非空且不为 "0" 就归为失败/瞬时。

所以京东现在**无论怎么写都不可能签到成功**（需要 h5st 签名，且活动本身没了）。
处理方式是归类为「平台受限」，而不是继续报"签到失败"让用户去重登 cookie。

### 架构改动：「平台受限」成为第三态（不再混进失败）

签到结果从两态变三态，全链路打通：

| 层 | 改动 |
|---|---|
| 平台客户端 | `checkin()` 多返回一个 `restricted: bool` |
| `checkin.py` | `run_cookie_acc` 返回 `(ok, desc, restricted)`；新增 `_report_result()` 统一打 `[OK]`/`[受限]`/`[FAIL]` 三种标；汇总行加「平台受限 N」；只有 fail 才让 exit code 非 0 |
| 日志 | 新标签 `[受限]` |
| `Models.swift` | `restrictedByDay` 桶；`status()` 优先级 **成功 > 受限 > 失败**；`todayFail()` **排除**受限账号 |
| Swift UI | 状态胶囊「平台受限」（`Theme.warn` 橙）、头像底色 `warnSoft`、行副文案显示受限原因；侧栏进度卡 / 分组摘要 / 完成通知都单列受限数 |

**关键设计**：`todayFail()` 必须排除受限账号，否则"失败自动重试"会拿着京东的
402 反复重试（`finishSign` 的重试轮次逻辑就是读 `todayFail`）。
另外 `AppModel.runSignSequence` 的实时刷新条件里也补了 `[受限]`。

  `is_already_msg("京东侧限制：…") == False`（受限不算已签到）；
  B站真实签到 → `[OK] 今日已签到（每日登录经验已到账，未重复领取）`；

## 第八轮：新增账号面板删掉「凭据导入」

**两者不是一回事**，但「凭据导入」确实是该删的那个。用户拍板：只删「凭据导入」。

### 两条路的真实差异（这是判断依据，别凭名字猜）

| | 凭据导入 | 手动粘贴 Cookie |
|---|---|---|
| 收什么 | 一整条 cURL 命令（抓包 Copy as cURL） | 只收 Cookie 字符串 |
| 走哪 | `curl_to_account.py` 解析成 `{method,url,headers,body}` | 平台原生客户端（bilibili/jd/lenovo） |
| 存成 | `accounts.json` 的 `requests[]` | `<platform>_auth.cookie` |
| 签到时 | `send_request()` **照原样重放**那次 HTTP 请求 | 走官方接口，**能校验、能读签到状态**（幂等/去重都靠它） |

### 关键 bug：输入框标签和实际行为不符（实测确认）

`curlForm` 的标签写「登录凭据（Cookie / Token）」，但 `parse_curl()` **只认 cURL**。
往里粘 Cookie 或 JWT **不报错**：

```
粘 "SESSDATA=abc123; bili_jct=xyz"  ->  GET SESSDATA=abc123;          # cookie 被当成 URL
粘 "eyJhbGciOiJIUzI1NiJ9..."        ->  GET eyJhbGciOiJIUzI1NiJ9...   # token 被当成 URL
粘 "curl 'https://...' -H '...'"     ->  POST https://...              # 只有这种是对的
```

也就是说：用户按标签提示粘 Cookie，会静默存成一个 `GET SESSDATA=…` 的账号，
签到时 `urllib` 抛 `unknown url type` 失败，界面上看不出任何异常。
**这一类"标签写 A、代码只吃 B、还静默成功"的入口必须清掉**，不能只改文案。

另外佐证：`accounts.json` 里 `requests` / `method` / `headers` 字段出现次数全为 **0**，
7 个账号没有一个用它，删除零影响。

## 第十轮：新增「什么值得买」与「阿里云盘」两个签到平台

用户从第九轮的候选清单里点了这两个（原话：「阿里云盘/什么值得买」）。

### 关键突破：不用真凭据就能验证接口

带**假凭据**打一发，只看错误响应形态，就能分辨「端点不存在 / 参数缺失 / 凭据无效 /
签名不对」。这一轮靠它把两个平台摸清了，也把什么值得买的签名算法**逐字节验证通过**：

- 五个端点全部存活：`auth.aliyundrive.com/v2/account/token`（400 InvalidParameterMissing）、
  `member.aliyundrive.com/v1/activity/sign_in_list`（401 AccessTokenInvalid）、
  `user-api.smzdm.com/checkin`（-1 "Sign param not enough"）、
  `zhiyou.smzdm.com/user/{checkin/jsonp_checkin,info/jsonp_get_current}`（200）。
- **smzdm 签名判别矩阵**（这是本轮最硬的实据）：
  | 用例 | 响应 |
  |---|---|
  | 无 sign | `-1 "Sign param not enough"` |
  | 错签名 / 错 key | `-1 "check Sign Fail"` ← 签名算法正确性的证明 |
  | 正确签名 + 空 cookie | `"11111" "请先登录" + logout:"1"` ← 凭据失效信号 |
  | 正确签名 + 假 cookie | `"11111" "貌似网络不太稳定"` ← 风控 |
  签名规则：按 key 字典序拼 `k=v&…` + `&key=<固定密钥>` → MD5 大写。
- 阿里云盘只读身份接口确认为 `api.aliyundrive.com/v2/user/get`
  （`adrive/v1/user/get` 是 404）。`sign_in_reward` 无 Authorization 头时要求
  `x-forwarded-user-id`，说明它靠 Bearer 推导用户。

### 新增文件

- **`smzdm.py`**：主路径走 App 端 `POST user-api.smzdm.com/checkin`（带签名），
  Web 端老接口作兜底。`_classify()` 把响应分三类：`ok` / `login`（凭据失效）/

## 第十二轮：签到页版式重构 + 修 30 天图 + 阿里云盘容量

自动签到那个开关了…阿里云盘没有积分，但它能检测到我有多少 G」。

### 版式原则：长明细一律下沉

根因不是"卡片排得不好"，是**行数 = 账号数**的区块（分账号余额、逐包额度）跟概览卡并排，
于是它的高度直接决定了整行高度，账号一多就把后面所有内容顶下去。三行重构：

| 行 | 内容 | 高度 |
|---|---|---|
| 1 | 今日总览 + 积分状态（只放总额 / 趋势） | **固定，不随账号数变** |
| 2 | 账号签到任务（全宽，上提到第二行） | 随账号数变（这是主内容，应该变） |
| 3 | 账号余额与额度 / 签到结果 | 随账号数变，但在最后，长也只影响自己 |

所以 `CreditCard` 拆成两个：`CreditCard`（概览）+ `BalanceCard`（明细，含可折叠的额度明细）。
真机上 9 个账号时第 1 行从 ~550pt 降到 ~266pt。

### 一并去掉的四处重复

1. **自动签到状态原来出现 4 次**：顶栏胶囊 / 总览卡右上胶囊 / 签到页 AutoSignCard /
   底部状态栏。现在只留顶栏胶囊；`AutoSignCard` 整个删除（设置页「定时签到」本来就是开关）。
2. **账号积分总额出现 2 次**（总览卡 metric + 积分状态卡大数字）→ 删总览卡那个。
3. **连续签到出现 2 次**（页头副标题 + 总览卡）→ 页头副标题只留"日期 + 上次签到"。
4. **底部状态栏**原本复述顶栏的"下次自动签到时间"，改为报**最近一次签到结果**
   （有失败/受限就说数量，正常就说已完成 N/T），圆点颜色也跟着数据走，不再是 launchd 状态。
   顺带删掉 `AppModel.greenText()`（唯一调用方在 ResultCard，已被更精确的文案取代）。
   ResultCard 也不再重复"今日共获得 N 积分"，红 banner 超过 3 条折叠成一行。

### 30 天柱状图滑不动：真因与修法

`BarChart` 是 `barW = max(10, min(26, raw))` —— 30 根柱在 ~300pt 里每根只能分到 ~8pt，
被下限顶到 10pt 后**总宽超出容器**，HStack 又是定宽 `.frame(width: geo.size.width)`，
于是右边直接裁掉、还滑不动；标签用 `.fixedSize()` 30 个挤在一起更没法看。
改成：先算 `needW = n*minBarWidth + (n-1)*gap`，装不下就套 `ScrollView(.horizontal)` 把
内容宽度撑到 needW，并用 `ScrollViewReader` 在 `.onAppear` / 切换天数时自动滚到今天
（数据由旧到新，不滚就一进来先看到 30 天前）。标签按天数稀疏：>21 天每 5 天一个、
>9 天每 2 天一个，不标的位置用不换行空格占位，否则柱子基线会参差。

### 阿里云盘容量（第三条「非积分资源」通道）

- 端点：`POST api.aliyundrive.com/v2/drive/get {"drive_id": <default_drive_id>}`
  → `total_size` / `used_size`（字节）。`/v2/user/get` **已不再返回** `personal_space_info`
  （老版本有），必须走 drive/get。真机读数：**剩余 337.3 GB / 共 681.2 GB**。
- 链路：`AliyunpanClient.space()` + `_user()`（user/get 缓存一次）→ `status()` 带出
  `capacity` → `checkin.py::_credit_record(capacity=…)` → `CreditInfo.capacity` → BalanceCard。
- **容量绝不进 balance**：否则 GB 会被 `totalCredits()` 当点数加进「账号积分总额」。
  阿里云盘的 balance 恒为 None，`unit` 记作"容量"。
- 顺手修了一个浪费：`_refresh()` 原来每次调用都刷一次令牌，而 status()/space() 都要用，
  于是同一次运行刷两三次（refresh_token 每刷一次都会轮换，刷太勤容易踩竞态）。
  现在按 `expires_in` 缓存 access_token，一次运行只刷一次（实测连打三次 → 刷新 1 次）。
