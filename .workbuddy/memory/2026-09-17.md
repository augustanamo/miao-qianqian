### 联想（lenovo.py，已改）

- 真实提交接口 = 前端 `signin.js` 的 `$.post($CONFIG.signPath, {...})`，
  参数：`_token`(=$CONFIG.token) / `memberSource`(=$CONFIG.userAgent，"0") /
  `pss` / `deviceId` / `deviceToken` / `lenovoId`。纯 H5 下后三个是空串
  （`pss` 只在原生 App 的 `HomeIntent.getP()` 存在时有值）。
- **响应形态**（实测）：
  - 首次成功：`{"success":true,"continueCount":1,"ledouValue":20,"scoreValue":10,
    "rewardTips":"获得20乐豆\n10积分\n2成长值"}` —— **没有 `code` 字段**，
    旧代码只认 code 会把成功判成失败。
  - 重复签到：`{"code":0,"msg":"用户已签到","postinfo":{...}}`
- **服务端抖动（关键发现）**：同一个 `_token`、同一份 cookie、同一套请求头，
  只有约 **20%** 的请求能过 CSRF，其余恒回 `419 {"message":"CSRF token mismatch."}`。
  用真实 Chromium 调页面自带的 `signSubmit()` 复现了同样比例（4 次里 3 次 419），
  且浏览器把数美 `deviceId`/`deviceToken` 都带上了照样失败 → **不是我们参数错，
  是对方 openresty 多实例、会话不粘**。人手在浏览器里点也会时好时坏。
  → 修法：`checkin()` 重试到成功（上限 20 次，签到接口幂等）。
  试过连接复用（keep-alive）、换字段、加上 X-XSRF-TOKEN 头，都不改善。
- **`GET /signuserinfo`**：乐豆 / 积分 / 延保券余额，前端 `getUserInfo()` 用的就是它。
  实测 `{"serviceAmount":77,"userCoins":1045,"ledou":"1.6万"}`。
  ⚠️ 两点：`ledou` 是站点四舍五入的展示串（"1.6万"，精度只到千位）；
  这个接口同样抖，未命中会话节点时回 `{"res":"Must login"}` 而 **HTTP 仍是 200**，
  所以必须按"有没有期望字段"判定并重试（同一会话反复打命中率约 35%，
  重建会话只有 ~10% → 刻意不重建，在同一个 `self._op` 上重试 15 次）。
- 页面已签标记：`$CONFIG.signState == "1"`（未签是空串）、`continuity_day` 递增、
  DOM 里 `<a class='immediate_active'> 已签到`。
- **本次实测该账号签到成功**：获得 20 乐豆 + 10 积分 + 2 成长值，
  之后 `checkin.py --only lenovo-13207607308` 回 `[OK] 今日已签到（幂等）`。

### 移动云盘：**能，已改为浏览器登录**（此前的判断过于保守）

此前把 caimcloud 归成 `LoginKind.manual`（只能手贴凭据），是错的。证据链：

- 社区多方口径一致：网页版 `yun.139.com` 登录后 **Cookie 里就有 `authorization`**
  （`@asunajs/caiyun`、青龙 `中国移动云盘.py`、AList/cloud139 文档都这么教）。
- 官方 Web bundle 自己就证明了：
  - `/w/` bundle 里有一张**存储键名表**：`x="authorization"`、`I="auth_token"`、
    `O="token"`、`v="a_k"`、`_="skey"`、`D="cutover_status"`、`P="nation_code"`，
    并且有 `C.set("Authorization", "Basic "+btoa(...))` —— JS 能写 ⇒ 通常不是 HttpOnly。
  - `/m/` bundle 里 Web 端**自己**就从 `window.VUEObj.$store.state.auth.authorization`
    取它来拼请求头。
- **Playwright 实测（未登录，只看结构）**：
  - 移动 UA + `/m/#/main` → `window.VUEObj.$store.state.auth` 存在，字段含
    `authorization`、`account`、`nickName`、`completeAccount`、`autoLoginPhoneAccount`、
    `nationCode` —— **两段（auth + 手机号）都在，一次取全**。
  - 桌面 UA 会被**重定向到 PC 版 `/w/`**；PC 版挂的是 `window.MCloudVM.$store.state.auth`，
    有 `account`/`accountPhone`，但**没有 `authorization`**（它只存在 Cookie 里）。
  - 桌面版首页 `https://yun.139.com/` 就是完整登录页（手机号 + 密码 + 验证码输入框都在）；
    ⚠️ `https://yun.139.com/w/#/login` 是 **404 页**，别写进 login_urls。

实现（改动面）：

- `browser_login.py`：新增 `_verify_caimcloud`（换 jwtToken 后读状态；账号名只取手机号后四位）、
  `_CAIM_SCRIPT`（VUEObj → MCloudVM → document.cookie 三级降级）、PLATFORMS 加 `caimcloud`。
- **`collect_cookie` 新增 `pair` 规则**（通用能力，别的平台以后也能用）：

### 华住会：技术上可以接，但凭据只能手贴、收益很小

- 签到接口：`GET https://appgw.huazhu.com/game/sign_in?date=<unix 秒>` + `Cookie` 头，
  **没有任何 JS 签名**（evilbutcher / yangtai 两版实现一致）→ 纯标准库可行。
- **网关有来源校验（本次关键发现）**：`appgw.huazhu.com` 是 **APISIX** 网关，
  缺 `Client-Platform` 头时恒回
  `429 {"code":429,"message":"You have been restricted, please try again later!"}`
  （与 Cookie 无关，假 Cookie 也一样）；带上该头才走到业务层，未登录回
  `401 {"code":1003,"message":"Unauthorized"}`。
  响应头里 CORS 暴露了它认的自定义头：`Client-Platform` / `sid` / `sk` / `version` /
  `User-Token` / `token` / `authorization`。
- ⚠️ **429 仍会随机出现**（同一头 `APP` 连打 3 次：1 次 401、2 次 429；`WECHAT` 也撞上 401）
  → 与联想同一类问题：**网关多实例限流计数不同步，正解是重试**，不要再去调参数。
- `game/sign_header`（社区抓 Cookie 用的那条）未登录回 `{"code":1003,...}`（端点活着）；
  `game/` 下其它路径回 `{"code":-107,"message":"divide:Can not find selector..."}`。
- 凭据来源：社区两版都从 **App / 小程序**抓（Loon 插件 MITM `appgw.huazhu.com/game/sign_header`；
  yangtai 走小程序 `hweb-minilogin.huazhu.com/bridge/jump?redirectUrl=...`）。
  官网 `www.hworld.com`、预订站 `hrewards.huazhu.com` 未登录 Cookie 里**没有任何登录态字段**，
  且**官网没有签到入口**（签到是 App 专属功能）。
- 结论：可接入，但要落成"手动粘贴 Cookie"型（`LoginKind.manual` 正好用得上），
  且签到收益很小（脚本作者自评"小小毛"，累计 7 天约 5 元券）→ **待用户决定是否接入**。

### 实测判决（2026-09，假凭据，**不带** SESSDATA）

- **活着，只要 cookie（POST 另需 `bili_jct`）**：`/x/vip/privilege/my`、
  `/x/vip/privilege/receive`(type=1/2)、`/x/vip_point/task/combine`、
  `/xlive/revenue/v1/wallet/getStatus`、`/xlive/revenue/v1/wallet/silver2coin`、
  `/x/web-interface/coin/add`、`/x/web-interface/coin/today/exp` → 全部 `-101 账号未登录`。
- **活着**（twirp 族用 HTTP 状态码）：`manga.../user.v1.User/GetVipReward` → `401 unauthenticated / need login`。
- **活着但要额外签名 → 先不做**：`/pgc/activity/score/task/sign2`、`.../receive/v2`
  → `-401 非法访问`（**同级**其它端点都是 `-101`，差异即签名/风控）→ 大积分那套成本明显更高。
- 对照：`/x/web-interface/share/add`、`/x/click-interface/web/heartbeat` **未登录也回 `code 0`**
  → 这类"未登录也给成功"的写接口**不能当"功能可用"的证据**（可能是静默 no-op）。

### 关键技术方法：**编造路径对照组**（已沉淀进 skill）

所有端点一开始都回同一个 `-400 请求错误`，此时错误码不携带信息。用编造路径校准：

| 请求（cookie 相同） | 结果 |
|---|---|
| 编造 `/x/vip/privilege/this_does_not_exist` | **HTTP 404 + HTML** |
| 编造 `/x/zzz_not_a_real_endpoint` | HTTP 404 + HTML |
| 真实 `/x/vip/privilege/my` | HTTP 200 + JSON |

判据：**回 JSON 业务体（哪怕 code 是错的）= 路由存在**；回 HTML/404 才是路径没了。
另外发现：**带假 `SESSDATA` → 一律 `-400`；不带 `SESSDATA` → 干净的 `-101`**
→ 探"路由是否存活"要**不带凭据**。（换一对有效 `buvid3/buvid4`，来自
`GET /x/frontend/finger/spi` 的 `data.b_3/b_4`，对 `-400` 毫无改善 → 不是指纹问题。）

## 修一个真漏洞：诊断让用户"重新登录"，账号页却没有入口（smzdm 触发）

用户原话：「我的什么值得买显示的是签到失败，因为是登录状态失效。但是你要是去账号页的话，
它又不能点重新登录。这个我感觉是有逻辑漏洞吧。」——**判断正确，是漏洞**。

### 复现与定位

- 真实日志（`logs/checkin.log`）：
  `[FAIL] smzdm-auto(smzdm) -> 签到失败：什么值得买登录态已失效，请重新登录后更新 Cookie（App：请先登录；网页：请先登录）（HTTP 200）`
- 三处入口各有各的问题，凑成了同一个洞：
  1. **账号行只有 `pencil` + `trash` 两个按钮**（重命名 / 删除）——**没有任何重新登录入口**。
     用户照着报错文案"请重新登录"来账号页，无处可点。
  2. 签到页异常弹窗的「去更新凭证」跳到账号页后**打开的是"新增账号"面板**
     （`m.showingAddPanel = true`），等于让人重新填一遍，也没带账号名走。
  3. 「凭证健康检查」卡把它算成"凭证正常"：判据是 `credentialHint().color != .green`，
     而 `credentialHint()` 对凭据型平台**只看字段非空**（`auth.isConfigured`）——
     Cookie 过期了也照样绿。所以卡片写着"10 个账号凭证均正常"，而其中一个是死的。
- 根因是一句话：**同一个事实被两处各判了一套**——弹窗按报错文案分类，账号页按字段非空。

### 修法（单一判据 + 就地入口）

- `AppModel.needsRelogin(_:)` 成为**唯一判据**，两个来源任一成立：
  ① 今天失败且 `CheckinIssue.diagnose().fix == .relogin`（**复用弹窗那套关键词表，不另写**）；
  ② `credentialHint()` 报红（凭据压根没填 / Trae token 过期）——不必等签到失败就该给入口。
  `isRetired` 恒 false。`canRelogin(_:)` 只判"平台有没有本机登录路径"。
- `AppModel.relogin(_:)` 按平台路由（WorkBuddy → `runWorkBuddyRefresh`、Trae → `runTraeLogin`、
  凭据型 → `runCookieBrowserLogin(type:name:)`），**沿用账号名**：
  `browser_login.save_cookie_account` → `cookie_manager.set_cookie` 同名即只改 auth 字段，
  **不会新增重复账号、也不动启用状态**（读源码确认过，这是这个入口敢直接给的前提）。
- **入口放在报错那一行末尾**（账号名下方第二行），不是操作列：报错文案和修它的按钮挨着最自然，
  且那一列宽度充足。刻意**不用**失败色红底胶囊——那看起来像又一个状态标签；
  用灰底 + 1px 描边（与 `SoftTag` 同一套语法：高 20 / 圆角 6 / 11.5pt）。
- 异常弹窗的 relogin 按钮改成**能就地解决就就地解决**（`m.relogin(a)`，标签按平台给），
  没有本机路径的平台才兜底跳账号页，并且**不再开新增面板**。
- 跳账号页时新增 `focusAccount` 高亮（淡红底 + 左侧 3pt 红竖条），点该行或离开页面即清掉
  （`selectedPage` 的 `didSet` 里清——**先切页、再设高亮**，顺序反了会被清）。
- 健康卡简化为 `isRetired → false` / `isWorkBuddy → wbHealthy == false` / 其余 `needsRelogin`。
